[2026-09-25 00:06] DECISION: AI grounding strategy — pass up to 5 most relevant dataset rows as JSON in the system prompt. Do not use a vector DB for MVP (overkill for <200 rows). Simple keyword match from the user's question against document_name and plain_explanation fields, then pass matching rows. REASON: The dataset is small; semantic search is unnecessary and adds latency + complexity. ALTERNATIVES: chromadb in-process (considered; rejected for complexity); full-text SQLite FTS5 (a reasonable middle ground, adding to backlog if time allows).

[2026-09-27 01:25] DECISION: Adopt the **explicit two-step search pattern** over the OpenRouter ":online suffix on the generation model" approach for live research. REASON: (a) it lets us control which sources get cited and record their URLs as a first-class field; (b) the generation step keeps using the existing OpenRouter→NVIDIA NIM chain, so search availability and generation availability are decoupled — a search-tier outage does not take generation down with it; (c) the raw findings are retained in the audit trail, so a synthesis failure can degrade to showing real sourced prose instead of losing the work. ALTERNATIVES: `:online` on the generation model itself (simpler, but couples search to generation and gives weaker control over citations); a third-party search API (Tavily/Brave/Serper) — rejected only because no such key is available in this environment, not on merit; it remains the better long-term choice and is a drop-in replacement behind `app/research/search.py`.

[2026-09-27 01:30] DECISION: Search-tier model order = `google/gemini-2.5-flash:online` → `openai/gpt-4o-mini:online` → `perplexity/sonar`. REASON: determined empirically against the actual account, not from docs. Perplexity `sonar` is the obvious paper-first choice but returns **HTTP 402 on this free-tier key**, so it is demoted to a best-effort third position. Both surviving models return real citation URLs in OpenRouter's structured `annotations` array, which is what the source-capture code reads. NOTABLE: `google/gemini-2.5-flash` *without* the `:online` suffix answers the same rate question from stale training data — it confidently quoted a November 2023 HDFC rate while the `:online` variant returned the correct current band. This is worth demonstrating live; it is the clearest possible evidence that the search step is real and not simulated. ALTERNATIVES: Perplexity `sonar-pro` (best citation quality, but also 402); `x-ai/grok-4.7` (reachable, but declined to answer rather than searching, and returned no citations — unreliable as a research step).

[2026-09-27 01:35] DECISION: Change the OpenRouter **generation** model from `meta-llama/llama-3.1-8b-instruct` to `openai/gpt-4o-mini`, keeping llama-3.1-8b as the second attempt and NVIDIA NIM as the final fallback. The provider chain (OpenRouter → NIM) is unchanged, as required. REASON: the research pipeline requests strict JSON over a ~6k-token grounding prompt. Measured: llama-3.1-8b returned prose or truncated JSON often enough that research runs were dropping into the unstructured fallback (observed: a full education-loan run collapsed to a single "Full researched answer" item). gpt-4o-mini returned valid parseable JSON on every attempt and costs ~$0.00005 per call, so the reliability gain is effectively free. ALTERNATIVES: keep llama-3.1-8b and just add a JSON repair pass (fragile, and would not have prevented truncation at the token ceiling); `deepseek/deepseek-v4-flash` (also works and is cheap, held as an untested third).

[2026-09-27 01:40] DECISION: Cache freshness = **7 days** for a whole entry, not per-field. REASON: a researched entry bundles a document list *and* a rate/fee band. Rates move in weeks; document requirements move in months. Taking the shorter window for the entry as a whole is the conservative choice, because a stale rate is more likely to mislead than a slightly stale document list. The 30-day document window and the 7-day rate window are both retained as named constants (`TTL_DOCUMENTS_DAYS`, `TTL_RATES_DAYS`) and recorded per-row in `cache_ttl_days`, so the policy can be made per-field later without a schema change. ALTERNATIVES: 30 days flat (cheaper to run, risks quoting a lapsed rate — unacceptable for a product whose selling point is "don't get caught out at the counter"); per-field TTLs now (more correct, but the pre-warm budget in the remaining time does not justify the extra complexity).

[2026-09-27 01:45] DECISION: RBI-vs-state attribution is **enforced in code, not just requested in the prompt**. `app/research/synthesize.py::_fix_state_misattribution` re-files any item the model placed under `rbi` that is textually a stamp-duty, registration, mutation or registrar matter, moving it to `state_stamp_act` or `registrar`. REASON: this is the single correctness rule the product exists to get right, and it is the rule a language model will most confidently violate — banks' own pages and aggregator content routinely talk about "loan documents" and "registration" in the same breath, and models pattern-match that into "RBI". Prompt instructions alone are not sufficient for a rule this load-bearing. The rewrite is logged in the answer as a correction rather than hidden. ALTERNATIVES: trust the prompt (measured as unreliable); drop the `rbi` bucket entirely (destroys a genuinely useful distinction — RBI *does* govern KYC and FEMA).

[2026-09-27 01:47] DECISION: Research runs on a **background thread + polling job API**, with automatic inline fallback. `POST /api/research/start` returns a job id immediately; the browser polls `/api/research/status/<id>` and drives the flip-board from real stage names and real source URLs as they arrive. If no progress is recorded for 3s (or 180s total), the polling request runs the research inline itself. REASON: a cold research call takes 15-40s, and Section 5 requires that latency be *shown* rather than hidden. A spinner over a blocked request gives the browser nothing to render and no stages to reveal. The inline fallback exists because the app must also survive a single-threaded or serverless runtime where a detached thread does not survive the response — without it the demo would hang forever on Vercel. ALTERNATIVES: synchronous request with a client-side fake progress animation (dishonest — the stages would be invented, and the brief explicitly wants real research shown); SSE/streaming (more moving parts than the win justifies, and awkward behind Vercel's buffering).

[2026-09-27 01:50] DECISION: **The agent itself (this session) acts as the research agent for the pre-seeded cache**, using its own web-search capability to gather sources and hand-structuring the findings into `research_cache` rows with real URLs, real `researched_at` timestamps, and the exact query text. REASON: the OpenRouter key hit its free-tier credit ceiling mid-session (total_credits 0; every model returns HTTP 402) and the user chose this route rather than waiting on a top-up. The seed rows are genuinely researched and genuinely sourced — they are not synthetic — and the live pipeline remains fully implemented and was verified working end-to-end before the credit ran out. Seed rows are flagged `is_seed = 1` so the app can distinguish curated seed content from live research, and the UI labels them honestly as pre-researched rather than implying they were fetched on demand. ALTERNATIVES: ship with an empty cache and rely entirely on live research (unacceptable for demo reliability); hand-write entries with no web verification (would violate the accuracy constraints in `.aimem/user-needs.md`); block all work until credit is restored (wastes the remaining ~19 hours).

REASON: Section 2 requires the app to answer for any transaction, and "Karnataka Bank's new gold loan scheme" is a legitimate query that must reach the research step. A closed enum would reject exactly the long-tail queries that demonstrate the product's actual claim. [2026-09-27 03:10] DECISION: `normalize_category` matches by **exact alias only** — the prefix-trimming walk was removed. REASON: found by reading the rendered page, not by a test. "Gold loan for senior citizens" was trimming backwards to "Gold loan", which meant (a) the user got a cached answer to a different, more specific question, and (b) it was a guaranteed cache hit on a question that had never been researched. Qualifiers carry the meaning, so anything that is not an exact alias must go to live research. `normalize_bank` and `normalize_state` keep prefix-trimming, because trailing tokens there are almost always noise ("HDFC Bank Ltd", "hdfc bank retail") and never change the answer. ALTERNATIVES: only trim when the remainder is a "complete" category (undecidable without a taxonomy, which the brief explicitly does not want); trim but mark such entries as approximations (worse — silently wrong is the failure mode we are removing).

[2026-09-27 03:15] DECISION: Both counters on the flip-board are pinned server-side to `len(str(total))` digits, and the JS `reserve()` call applies that width to **both**. REASON: measured, not assumed. With `data-min="1"` on the done counter and `data-min="2"` on the total, the board was geometrically stable from 0-9 and would have gained a cell — and shifted ~26px sideways — the moment the user reached 10. On a 14-item checklist that is a certainty, not an edge case, and the brief names this component as the demo centrepiece. ALTERNATIVES: CSS-only fix (cannot know the total's digit count); JS-derived width (would flash on first paint before the script ran — the width must be right in the server-rendered HTML).

[2026-09-27 03:20] DECISION: The status badge gets `min-width: 112px`. REASON: measured. "Pending" and "Done" rendered 96px, "In progress" rendered 108.5px, so the badge resized between states and pushed the step title sideways. 112px is 14x8 and fits the longest label with air. ALTERNATIVES: shorter labels ("Getting it", "Have it") — vaguer; per-state min-widths (the badge would still move, just less).

[2026-09-27 05:30] DECISION: On research failure the board is relabelled "Research stopped", the pulse animation is paused, and the "we are searching the web" note is withdrawn — the retry path restores all three. REASON: verified against the real 402 response with search genuinely down. The first implementation left the board reading "RESEARCHING LIVE" with an animated pulse and a note saying Kaagaz "is searching the web" *directly beneath* a message saying it could not. Everything still functioned and every automated check passed, but the page was visibly lying to the user, and this is precisely the moment a demo audience is most likely to be looking. The same shape of bug appeared twice more in this build (the board label disagreeing with the ticker, the source pills never rendering because the container was a sibling of the element the ticker bound to) — all three are "the element is present and the code ran, but it is not saying what is true". ALTERNATIVES: leave it and rely on the error message alone (insufficient — the contradiction is above the message); remove the board entirely on failure (loses the elapsed-time evidence that the attempt was real).

[2026-09-27 05:50] DECISION: Make the SQLite path resolve at runtime — `DATABASE_PATH` override, then `instance/`, then `/tmp/`, then `:memory:` — and auto-seed the research cache on startup when it is empty. REASON: the Phase-1 `vercel.json` would have taken the app down on its first write. The Vercel deployment bundle is read-only and only `/tmp` is writable, so `instance/kaagaz.db` raises, `seed_db` swallows nothing, and the app 500s at import. This was invisible locally and would have been found the worst possible way. The auto-seed is the other half: on a cold serverless start `/tmp` is empty, so without it the deployed instance would answer *every* question with a 15-40 second research call and look broken — the seed data is bundled, so the fix is to rebuild the cache on boot rather than to warn about it. The `:memory:` last resort exists so a completely unwritable environment still serves requests and reports its own degraded state rather than failing to start. ALTERNATIVES: require a real database (Postgres etc.) — correct in principle, wrong for the remaining time and for a submission that must run from a single `flask run`; keep `instance/` and add a Vercel-specific build hack (fragile, and the bug returns on the next platform); document the limitation and ship it broken (unacceptable — the brief's reliability section is explicit).

[2026-09-27 05:55] DECISION: Add `GET /api/research/health` reporting database writability, cache state and key presence, and it never returns non-200. REASON: a deployment that cannot be verified in one HTTP call is a deployment that gets verified by loading a page in a browser and hoping. Health checks that fail on a missing optional key are worse than useless — they produce a red dashboard for a condition the app handles gracefully, so this endpoint reports the *truth* and always returns 200. The `TestDeployment` suite then pins the property that actually matters: a cold start at a brand-new path auto-seeds and all ten demo cases still answer from cache.

[2026-09-27 06:05] DECISION: Replace model-native web search as the **primary** search step with a direct, keyless pipeline: DuckDuckGo's HTML endpoints for the result list, then fetch the top five pages in parallel and strip them to text, then feed that real page text to the generation step. Model-native (`:online`) search is demoted to a fallback for when the direct path is blocked. REASON: (a) it removes the API-credit dependency entirely, which was the one thing blocking the demo's key moment; (b) it is *better* grounding — the synthesiser reads the actual page rather than another model's summary of it, which is precisely the "explicit two-step tool-use pattern" the brief describes and the one it says "gives you more control over which sources get cited"; (c) citations become exactly the set of pages that returned readable text, so nothing is cited that was not opened. Measured: 10 results found, 5/5 pages fetched (2.9k-6k chars each), bank's own product page ranked first. ALTERNATIVES: Brave/Tavily/Serper/Exa (all need keys — no key available); Wikipedia (wrong domain — bank document checklists are not encyclopaedia entries); public SearXNG instances (tested three: two returned HTTP 429, one DNS-failed); Marginalia (returned only its own navigation links); Mojeek (200 but zero parseable results); DuckDuckGo's instant-answer API (real, but only returns an abstract, not a result list).

[2026-09-27 06:10] DECISION: Detect DuckDuckGo's anti-bot response explicitly (HTTP 202/429/503, or challenge markers in the body) and treat it as a distinct condition, retried with bounded backoff (0/8/20s, total under 60s) before falling through to the second backend. REASON: DDG does not return an error when it blocks you — it returns **HTTP 202 with a ~14KB challenge page**. The first version treated that as success, parsed zero results, and reported "No search backend available", which is true and completely useless: the real cause was throttling the process had caused itself, and the message sent every reader looking at the provider list instead of at a rate limiter. Measured: my own burst of ~8 test queries earned a block that persisted well past 5 minutes. ALTERNATIVES: ignore it and accept a hard failure (worse — a transient condition becomes a user-visible error); report throttling as "no results" (the original bug); drop the keyless engine and require a paid key (back to where we started).

[2026-09-27 06:15] DECISION: Rank search results by source authority before fetching: regulator/government first, then the named bank's own domain, then everything else — stable within each tier so DuckDuckGo's own relevance order is preserved. And run a second query biased at the bank's site only when the first did not already surface an authoritative source. REASON: measured. A single generic query for "home loan at State Bank of India documents required" returned two Scribd document previews and three aggregators, with `homeloans.sbi.bank.in` ranked out of the top five entirely. Grounding a checklist in listicles is how you get a confidently wrong answer with citations attached. ALTERNATIVES: filter to official domains only (rejects every bank we have not heard of, which is the product's whole claim); trust DuckDuckGo's ranking (demonstrably listicle-dominated for this query shape); fetch all ten and let the model choose (slower, and still dominated by the same SEO pages).

[2026-09-27 06:20] DECISION: Point NVIDIA NIM at `nvidia/nemotron-3-super-120b-a12b` as primary, with `mistralai/mistral-nemotron` and `meta/llama-3.2-11b-vision-instruct` behind it. The Phase-1 NIM model (`meta/llama-3.1-8b-instruct`) now returns HTTP 410 Gone. REASON: determined by sweeping all 82 models the NIM account advertises and finding that only 13 actually answer a completion request — the list is mostly endpoints that 404. Of the 13, measured on a real JSON-mode research request: nemotron-3-super 2.7s valid JSON, mistral-nemotron 2.1s valid JSON, llama-3.2-11b 1.8s valid JSON. `nemotron-3.5-lightning-30b` was excluded: it emits visible reasoning before the answer and returned non-JSON after 58s. This means the generation step is free and needs no key at all, which is what makes the whole pipeline runnable with zero credentials. ALTERNATIVES: keep llama-3.1-8b (410 Gone, dead); use only the fastest model (mistral-nemotron at 2.1s, but 120b is meaningfully better at long grounding prompts — quality over 0.9s).

[2026-09-27 06:25] DECISION: Make the whole Python suite network-free by stubbing the AI provider at the route boundary, and assert the degradation path deterministically. REASON: the suite was documented as "no network, no keys" and had quietly stopped being true — once NIM started actually answering, the `/api/ai/explain` tests silently became live integration tests and the run went from 5s to 140s. A suite that is slow because it is making real calls is a suite that gets skipped, and a skipped suite catches nothing. One test (`test_ask_endpoint_still_answers_without_any_keys`) also now stubs the search step so it tests the degradation contract rather than inheriting whatever a public search engine feels like return that day. 162 tests, 1.7s. ALTERNATIVES: leave the live tests and accept a 140s suite (works, but the property that makes the suite trustworthy — determinism — is gone); delete the AI tests (throws away real endpoint coverage).

[2026-09-27 06:45] DECISION: Extend the pre-researched seed set from 10 to 14 entries — personal loan, Kisan Credit Card, vehicle loan (HDFC, car and two-wheeler) and loan against property (HDFC). REASON: the brief calls this "a bonus, not a requirement", but with the live path rate-limited it is the highest-value use of the remaining time, and each addition widens the demonstration rather than duplicating it. Personal loan is the most-borrowed retail product in India and the two banks make a sharp contrast on income proof. KCC is the one seed where the RBI sets most of the rules itself and where linked Aadhaar decides whether you get 7% or the MCLR-linked rate — a genuinely different regulatory shape. Loan against property is the deliberate contrast with home loan on LTV and tax benefit. 32 distinct primary sources now, up from 24. ALTERNATIVES: more banks per existing product (less interesting than more products — the claim is coverage, not bank count); deeper checklists for existing entries (diminishing returns; the existing ones already run 10-14 items).

[2026-09-27 06:50] DECISION: Fix a database-seeding regression that would have broken every fresh install, and add a schema test rather than a behaviour test for it. REASON: the serverless fix from earlier introduced it. `_resolve_database_path` probed the target file with `open(candidate, 'a')` to test writability — which *creates* the file. `db_seed.seed_db` then saw a file already present, concluded "already seeded", and returned without creating a single table. So a fresh clone would start with a database containing only `research_cache` and 500 on the first checklist page. It survived an hour of testing because the development database already existed with its tables, `init_schema` creates `research_cache` unconditionally so every research test still passed, and my cold-start test only asserted the research side. Found by deleting the database and starting again. The fix tests the *directory's* writability rather than the file. The lesson is about the test, not the code: asserting "the demo answers" is not the same as asserting "the database is correctly schema'd", and only the second would have caught it. ALTERNATIVES: probe the file and delete it if absent (works, but leaves a race between the probe and the seed); have `seed_db` check for the table rather than the file (also correct, and belt-and-braces — but the probe side effect is a trap for the next thing that touches the path, so it was removed as well).

[2026-09-27 06:55] DECISION: Add **Groq** as the second provider in the generation chain (OpenRouter -> Groq -> NVIDIA NIM), and refactor the hardcoded per-provider functions in `app/ai/client.py` into one ordered `PROVIDERS` registry. REASON: Groq sits between OpenRouter and NIM because it is *faster than both* (measured 0.9s with valid JSON on a real research request, against 2.1-2.7s on NIM) and has a usable free tier, so it should absorb the load before the slowest provider. The refactor was not cosmetic: with three providers the per-provider `if/else` in `generate()` and `generate_json()` was already duplicated, and a fourth would have made it unmaintainable. ALTERNATIVES: Groq in place of NIM (worse — NIM is the only provider here with no meaningful rate limit, and dropping the third fallback leaves the chain brittle); Groq appended last (leaves every call paying a 402 on OpenRouter and a slow NIM round trip before reaching the fastest provider).

[2026-09-27 07:00] DECISION: **Discover Groq's model list from `/models` at runtime** rather than hardcoding it, filtered to instruction-following families and ordered by preference, with the static shortlist as a fallback. REASON: not theoretical — verified against the live account. `llama-3.3-70b-versatile` and `llama-3.1-8b-instant`, the two slugs any hardcoded list would have named, **return HTTP 404 — they do not exist on this account**. The catalogue is 11 models, of which the usable ones are `openai/gpt-oss-120b` (0.9s, valid JSON), `openai/gpt-oss-20b` and `qwen/qwen3.8-27b`. [2026-09-27 07:05] DECISION: Exclude moderation and speech models from the Groq chain (`*-guard-*`, `*-safeguard-*`, `whisper-*`, plus audio/TTS/embedding). REASON: a moderation model asked for a JSON checklist returns a safety verdict, which parses as a *successful* call and yields a wrong answer — strictly worse than having no model. Caught while reading the real catalogue back: `openai/gpt-oss-safeguard-20b` and two `llama-prompt-guard-*` slugs are all present and would all have passed a naive "matches llama" filter. ALTERNATIVES: rely on the provider to route around them (it does not); keep them as last-resort fallbacks (a nonsense answer is not a fallback).

[2026-09-27 07:10] DECISION: Add a **circuit breaker**: skip providers with no key, and trip out those answering 401/402/403/404/410/429 for five minutes. REASON: the OpenRouter key on this project is a free tier with no credit, so every generation was opening with a guaranteed ~200ms HTTP 402 before reaching a provider that works. That is dead latency on every single call, forever. Only *terminal* statuses trip a provider: a 500 or a 400 is one bad call, not grounds for abandoning a provider for five minutes, and treating them the same would have made the chain needlessly brittle. After the grace period a provider is retried, because a key can be topped up mid-session and nothing signals that except trying again. ALTERNATIVES: leave the 402 in place and accept the latency (measurably wasteful); trip on any error including 5xx (turns a transient provider blip into a five-minute outage); permanent disable on first failure (no recovery path).

[2026-09-27 07:15] DECISION: Move the trip decision out of the HTTP transport and into `call_provider`. REASON: it was initially written inside `_post`, which made it untestable — any test that stubbed `_post` bypassed the very behaviour it was trying to test, so the breaker looked covered and was not. The retry *policy* belongs next to the code that decides whether to retry, not inside the thing that moves bytes. ALTERNATIVES: test the breaker with a live 402 (needs a real out-of-credit key and is slow and flaky); keep it in `_post` and mark the test skipped (the first version did this, which is how the gap survived).
