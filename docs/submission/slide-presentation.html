The problem

Paperwork fails at the counter.

India · banking & financial
transactions

Nobody finds out early

The missing affidavit, the attestation not done abroad, the stamp denomination nobody mentioned — all of it surfaces during the appointment.

Scattered across four sources

Bank product pages, RBI circulars, state stamp-duty schedules, registrar notices. None of them agrees on a single list.

The regulators get conflated

“The RBI says you need stamp duty” sends someone to entirely the wrong government office — and it is the most common error in the domain.

No cost, no timeline

A list of names is not a plan. What it costs, how many days each step takes, and which one blocks the next is what makes it usable.

The same question has four different answers. One per residency status — and more again per state, because stamp duty and registration fees are state law.

Ask an NRI for a resident’s checklist and you get a list full of documents they do not need — and no work permit, no attested contract, no overseas statements.

What it costs in practice

Repeat visits, missed appointment slots, and occasionally a missed disbursement deadline. The information existed the whole time — it was just never in one ordered place.

Kaagaz · the problem 02

Why the obvious build fails

A checklist app has a ceiling set by its curator.

The obvious approach

  • Someone decides which transactions matter and hand-writes the list.
  • It covers exactly those cases, and nothing outside them.
  • It goes stale the week a bank revises a fee schedule.
  • Nobody can tell which regulator imposed which line.

What Kaagaz does instead

  • Free-text question. Unknown banks and products are researched, not rejected.
  • Search the live web, read the pages, cite only what was opened.
  • Freshness is per entry, with an as-of date on screen.
  • Regulator attribution is enforced in code, not requested in a prompt.

Questions a fixed list cannot answer

“Kisan Credit Card renewal for a Kisan with 2 land records”

Not one of the four canonical products, and the document set depends on how many land records exist.

“Gold loan at a small finance bank, not HDFC”

A bank nobody curated. It is still researched, ranked by its own name match, and cited from its own pages.

“Property registration in Kerala for an NRI buyer”

State fees and residency rules and an attestation chain, all at once — the case a single-list product gets wrong most often.

The cache is a floor, not a ceiling. 14 answers are pre-warmed so the common cases are instant and the demo survives a bad network. Anything else goes out to live search and is filed into the same record.

Correct misattribution, reject unsourced figures, clamp nonsense costs.

File

One row: answer, sources, query, timestamp, model, provider.

Why search and generation are separate

  • They are independent failures — a search outage does not disable structuring.
  • Retrieval grounds the model in real page text, not another model’s summary.
  • We choose which sources get cited, rather than hoping the model does.

What the user sees while it runs

Checking sources Reading pages Building checklist

Real stage names from the server, and the source hostnames as each page is actually fetched. Nothing on that board is simulated.

A 202 from DuckDuckGo is a block, not an empty result. Detected explicitly, given one short retry, then reported as a throttle — never rendered as “no results”.

Freshness

Document lists move slowly, rates move weekly — so an entry takes the shorter window. Every row stores its own TTL.

Degradation order

Fresh hit → stale answer labelled with its age → live research → related cached cases. An error is the last resort, never the first.

Cold start

On a blank database the schema is created and the seed set filed automatically. There is no setup step to forget.

Kaagaz · architecture 05

Resilience

One registry, three providers, no single point of failure.

OpenRouterbest structured output
Groqmeasured 0.9s, valid JSON
NVIDIA NIMfree tier, slowest
  • No key is skipped, not called and failed. An unauthenticated round trip on every request is pure waste.
  • Out of credit trips the provider out for five minutes, so no call opens with a guaranteed 402.
  • Only terminal statuses trip it. A 500 is one bad call, not grounds for abandoning a provider.
  • Groq’s model list is discovered, not hardcoded — verified against the live catalogue.
  • Moderation models are excluded. A guard model answering a JSON request looks like success and returns nonsense.
  • Nothing is invented on the way down the chain — if every provider fails, the app degrades instead of guessing.

Kaagaz · resilience 06

Accuracy

It says what it could not confirm.

the app’s own disclosure block
sources read for this answer

Both panels are lifted straight from one result page, unmodified.

Never invented

A cost or rate with no source becomes “not publicly disclosed — contact the bank directly.” Inverted and absurd ranges are repaired, not prettied.

Never misattributed

Stamp duty and registration are re-filed to the state or registrar after generation. The prompt asks for the right answer; the code guarantees it.

Bands, not guarantees

Real pricing depends on credit score, amount and tenure, so every rate is a published band.

Kaagaz · accuracy 07

Provenance

Any answer can be taken apart.

The cache row is the audit trail

  • The exact query that produced this answer.
  • Every source URL that was actually read.
  • When it was researched, and when it goes stale.
  • Which model and provider structured it.

Nothing is cited that was not opened. A URL only becomes a source if the fetch returned readable text — so the citation list is exactly the set of pages that were read.

Why the cache is trustworthy

A pre-warmed entry is marked as such on screen and is not presented as a live lookup. The freshness window is stored per row, so a rate cannot outlive the page it came from.

Kaagaz · IBM Bob 10

Honest limits

What this is, and is not.

Known limits

  • Informational only. Not legal or financial advice.
  • Cold research needs a reachable search provider; when blocked it shows overlapping cached cases instead of failing blank.
  • English only. Coverage is exactly as good as public sources are.

Next

  • Persist the research record so the cache survives restarts.
  • Per-field freshness — rates move weekly, document lists monthly.
  • Regional languages, and upload-based verification.

Tradeoffs we chose deliberately

SQLite, not Postgres

One writer, one process, one file. Correct for this. Scaling out means migrating off it — a different project, not a config change.

Keyless search, not a paid API

Costs nothing and works with no keys, which is why the whole app runs free. The trade is that it can be rate-limited.

Grounding, not a bigger model

Reading the real pages beats asking a larger model to summarise them, and it is what makes the citations checkable.
